## 上下文

Editor 页面当前使用分散的 `useState` 管理状态，包含：
- 标注数据：`arrows`, `rects`, `texts`, `mosaics`
- 选中状态：`selectedArrowId`, `selectedRectId`, `selectedTextId`, `selectedMosaicId`
- 视图状态：`scale`, `offset`
- 图片数据：`imageData`, `source`

工具栏已存在撤销/重做按钮但被禁用，缺乏历史记录机制。

## 目标 / 非目标

**目标：**
- 实现完整的历史记录功能，支持撤销/恢复
- 支持所有标注操作的历史记录
- 支持裁剪操作的撤销
- 提供直观的键盘快捷键和 UI 交互

**非目标：**
- 不实现跨会话的历史持久化（刷新页面后历史清空）
- 不实现历史记录的可视化列表（仅支持线性撤销/恢复）
- 不修改现有标注的数据结构

## 决策

### 1. 状态管理方案

**决策：使用 Zustand + 自定义 Hook**

理由：
- 项目已有 Zustand 使用案例（`capture-store.ts`）
- Zustand 轻量级，适合 Chrome 扩展
- 可与现有 useState 共存，渐进式重构

考虑的替代方案：
- Redux：过于重量级，不适合当前规模
- useReducer：需要大量样板代码，状态分散难以管理
- 纯 useState：历史记录难以实现，状态快照复杂

### 2. 历史记录策略

**决策：快照模式（Snapshot）**

采用 `past[] + present + future[]` 三栈结构：

```
past: [state1, state2, state3]
present: state4
future: []
```

理由：
- 实现简单，无需理解命令模式
- 状态完整，恢复可靠
- 性能可接受（标注数据量小）

考虑的替代方案：
- 命令模式（Command Pattern）：需要定义所有操作类型，实现复杂度高
- 增量差异模式：需要 diff/patch 算法，调试困难

### 3. 裁剪操作处理

**决策：裁剪时保存完整状态快照**

裁剪操作会修改图片数据，需要保存：
- 原始图片数据
- 所有标注数据
- 视图状态

理由：
- 裁剪是不可逆操作，需要完整快照才能恢复
- 标注在裁剪后会被清除，需要保留原标注

### 4. 历史记录限制

**决策：最大 50 条历史记录**

理由：
- 避免内存过度占用
- 50 条足够满足一般编辑需求
- 可后续通过配置调整

## 风险 / 权衡

| 风险 | 缓解措施 |
|------|----------|
| 内存占用增加 | 限制历史记录条数（50 条） |
| 状态同步问题 | 使用 useRef 同步最新状态 |
| 快捷键冲突 | 避免在输入框聚焦时触发 |
| 性能影响 | 使用浅比较避免不必要渲染 |

## 迁移计划

1. 创建统一状态类型定义
2. 实现 `useEditorHistory` Hook
3. 重构 Editor 状态为统一结构
4. 集成历史记录到所有状态变更点
5. 启用撤销/重做按钮并添加快捷键
6. 测试验证

**回滚方案：** 保留原有 useState 代码，可快速回退
