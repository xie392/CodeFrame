## 上下文

editor 页面是 CodeFrame 的图片编辑器核心功能，对标 ShotEasy 的截图标注功能。当前 editor 页面仅为骨架状态（69 行），仅有基本的工具栏 + 画布 + 属性面板布局占位，无实际功能。需要基于 ui.pen 中的 Editor 设计稿和 CodeGen - Light 的 Light 主题风格，实现完整的 UI 框架。

### 约束
- 每个页面是独立的 React 应用实例，通过 `chrome.tabs.create()` 导航
- 页面间数据传递通过 `chrome.storage.local` 或 URL 查询参数
- 必须兼容 Manifest V3（无 eval、无内联脚本等 CSP 限制）
- UI 风格参考 ui.pen 中 CodeGen - Light 的 Light 主题设计

## 目标 / 非目标

### 目标
- 实现编辑器页面的完整 UI 布局框架（工具栏、画布区、属性面板）
- 实现 popup 到 editor 的跳转逻辑（两种模式）
- 实现截图完成后自动携带图片数据跳转到 editor
- 支持从空画布模式手动上传或粘贴图片

### 非目标
- 标注工具的具体交互实现（箭头、矩形、文字、马赛克等）留到后续变更
- 图片裁剪、旋转、滤镜等编辑功能
- 属性面板的具体编辑控件实现
- 导出功能

## 决策

### 1. 页面进入方式设计

**决策**：通过 URL 查询参数区分两种进入模式

- 带图模式：截图完成后，将截图数据写入 `chrome.storage.local`，然后通过 `chrome.tabs.create()` 打开 editor 页面，URL 带 `?source=capture` 参数
- 空画布模式：popup 直接打开 editor 页面，URL 无参数或带 `?source=upload`

**理由**：URL 参数是 Chrome 扩展页面间传递简单状态的最直接方式，无需引入额外的状态管理。图片数据通过 `chrome.storage.local` 传递避免 URL 过长。

**替代方案**：使用消息传递 — 但 editor 是独立页面，需要在页面加载后监听消息，时序复杂度更高。

### 2. 图片数据传递

**决策**：截图结果通过 `chrome.storage.local` 的 `CAPTURE_RESULT` 键传递（已存在）

**理由**：复用现有的存储键和数据结构（`CaptureResultPayload`），减少重复定义。

### 3. UI 布局方案

**决策**：三栏布局 — 左侧工具栏（56px）+ 中央画布（flex-1）+ 右侧属性面板（280px）

参考 ui.pen 中 Editor 设计稿：
- 工具栏：毛玻璃效果背景，工具按钮 40x40 圆角 12，分隔线
- 画布区：图片居中显示，支持缩放
- 属性面板：毛玻璃效果背景，显示选中工具的属性

### 4. 空画布模式的上传交互

**决策**：空画布模式下显示上传提示区域，支持拖拽上传和点击选择文件，同时监听全局粘贴事件

**理由**：与 codegen 页面的空状态交互保持一致，用户可以通过三种方式（拖拽、点击、粘贴）导入图片。

## 风险 / 权衡

- **大图片存储风险**：截图数据以 base64 存入 `chrome.storage.local`（上限 10MB），高分辨率截图可能接近上限 → 缓解措施：截图时控制分辨率，或后续改用 IndexedDB
- **UI 仅静态框架**：工具按钮和属性面板暂无实际交互 → 后续通过单独变更逐步实现
